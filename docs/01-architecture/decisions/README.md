# Architecture Decision Records (ADR)

> Что такое ADR, когда его заводят, как он выглядит и указатель на все записи. Открывать перед
> тем, как менять принятое решение или записывать новое.

ADR — короткая запись о **значимом** решении: контекст, варианты, выбор и последствия. Цель —
чтобы через полгода было понятно, **почему** так, а не только **как**.

## Когда заводить ADR

- Выбор между несколькими реальными подходами с долгоиграющими последствиями.
- Решение, которое дорого откатывать.
- Любой случай, когда хочется написать «мы же договаривались…».

## Формат

Каждый ADR — отдельный файл `NNNN-kebab-slug.md`: номер по порядку с `0001` без пропусков, имя
латиницей. Внутри:

```
# ADR-NNNN: Заголовок

- **Статус:** предложен | принят | отклонён | заменён [ADR-XXXX](XXXX-….md)
- **Дата:** YYYY-MM-DD
- **Заменяет:** [ADR-XXXX](XXXX-….md) — только у записи, которая заменила другую

> Врезка: что решено и когда это читать.

## Контекст      — какую проблему решаем, какие ограничения
## Варианты      — что рассматривали, с плюсами и минусами
## Решение       — что выбрали и почему
## Последствия   — что из этого следует, хорошее и плохое; триггер пересмотра
```

**Принятый ADR не переписывается.** Решение изменилось — новый ADR со строкой `Заменяет:`, а у
старого статус меняется на «заменён ADR-XXXX», и это единственная правка старого текста. Находка
после факта, которая решения не меняет, дописывается в конец того же файла датированным разделом
`## Дополнение ДД.ММ.ГГГГ`.
